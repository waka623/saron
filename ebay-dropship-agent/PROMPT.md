## 0. あなた(Claude Code)の役割とゴール

あなたはシニアのバックエンド/自動化エンジニアです。eBay 上で **卸直送型の無在庫ドロップシッピング** を運営するための、
**PDCA を自動で回す運用エージェント** を設計・実装します。

最終ゴールは次の 1 文で表せます:

> 「商品リサーチ → 出品 → 価格・在庫の監視 → 受注処理 → 実績分析 → 改善案の生成」までを
> システムが自律的に回し、**リスクを伴う操作だけは人間の承認を挟んで** 実行するエージェント。

重要なのは全自動そのものではなく、**規約を守りながら、人間が承認ボタンを押すだけで運用が前進する状態** を作ることです。

## 1. 絶対に守る制約(コンプライアンス — 最優先)

以下はビジネス上・アカウント存続上のクリティカルな制約です。**コードとロジックの設計はこの制約に従属します。**
迷ったら安全側(何もしない/承認待ちにする)に倒してください。詳細は `compliance.md` を参照。

1. **仕入れ元は「卸・サプライヤーからの直送」に限定する。**
   Amazon・Walmart・他の小売サイトから購入して顧客に転送する *retail arbitrage(小売アービトラージ)* は
   eBay で禁止されており、アカウント停止の対象です。サプライヤーは「卸/ドロップシップ提携先」を前提に設計してください。
2. **承認ゲート(Human-in-the-loop)を必ず通す操作:**
   - 新規出品の公開(publish)
   - 価格の変更(値上げ・値下げ)
   - 出品の取り下げ・在庫切れ処理
   - 顧客への発注(サプライヤーへの購入)
   これらは **必ず「提案 → 人間の承認 → 実行」** の 3 段構成にします。承認なしで外部に副作用を出してはいけません。
3. **公式 API のみを使う。** スクレイピングや非公式の自動操作は使わない。eBay の Sell API 群を正規に利用します。
4. **レート制限を尊重する。** eBay API には日次コール上限があります。指数バックオフ・リトライ・
   コールバジェット管理を実装し、上限に近づいたら自動で減速・停止する。
5. **納期と在庫の正確性を担保する。** 無在庫では「注文が入ったのにサプライヤー在庫がない」が最大の事故。
   在庫・価格はサプライヤー側を定期同期し、乖離時は自動で出品を保留(承認待ち)にする。
6. **利益ガード。** 手数料(eBay 手数料・決済手数料・送料)を差し引いた **純利益がしきい値を下回る価格改定は自動提案しない**。
7. すべての「実行された副作用」は監査ログに残す(誰の承認で・いつ・何を・結果どうなったか)。

> 実装中にこれらの制約と機能要求が衝突したら、機能を削ってでも制約を優先し、その判断をコメントと `DECISIONS.md` に記録すること。

## 2. スコープ(MVP の範囲)

- **対象プラットフォーム:** eBay のみ(将来のマルチPF化を見越し、PF依存部分は `adapters/` に隔離)。
- **在庫モデル:** 無在庫ドロップシッピング(卸直送)。
- **自動化レベル:** 承認付き自動実行(提案は自動、実行は承認ゲート)。
- **MVP に含む:** リサーチ、出品ドラフト生成、承認、公開、価格/在庫監視、受注取り込み、実績分析、改善提案(PDCA)。
- **MVP に含まない(将来拡張):** 複数PF展開、広告(Promoted Listings)最適化の自動入札、A/Bテストの完全自動化、多通貨・多国展開。

## 3. PDCA ループの定義(このエージェントの心臓部)

各サイクルは次の 4 フェーズで構成し、`orchestrator` がスケジュール実行します(初期設定:**日次 1 回**)。
**各フェーズの出力は必ず構造化データ(DBレコード)として残し、次サイクルの入力にします。**

- **Plan(計画):**
  リサーチ結果(需要・相場・競合・利益シミュレーション)から「出品候補」と「価格戦略」を生成する。
  出力:出品候補リスト、目標価格、想定利益率、根拠。
- **Do(実行):**
  承認済みの候補を eBay に出品/価格改定/受注処理する。**未承認のものは実行しない。**
  出力:実行結果(成功/失敗)、API レスポンス、監査ログ。
- **Check(評価):**
  一定期間の指標を集計する:インプレッション、閲覧数、ウォッチ数、成約率(sell-through)、
  実利益、返品率、在庫乖離、価格競争力。目標との差分を出す。
- **Act(改善):**
  評価結果から次アクションを **提案** する:値下げ/値上げ、出品文・タイトル・カテゴリの改善、
  不採算商品の取り下げ、勝ち筋商品の横展開。提案は承認キューに積む。

各サイクルの開始・終了・KPI・生成提案は `cycles` テーブルに記録し、後から「なぜこの判断をしたか」を追跡できるようにする。

## 4. システム・アーキテクチャ

疎結合なモジュール構成にする。各モジュールは単体テスト可能なインターフェースで区切ること。

```
ebay-dropship-agent/
├── PROMPT.md, AGENT_PROMPTS.md, compliance.md, CLAUDE.md, DECISIONS.md, README.md
├── .env.example
├── pyproject.toml
├── data/                     # CSVサプライヤー連携用のローカルデータ置き場(gitignore対象)
├── src/ebay_dropship/
│   ├── orchestrator/         # PDCA スケジューラ。各フェーズを起動し状態遷移を管理
│   ├── research/             # 需要・相場・競合分析、利益シミュレーション(Browse/Analytics API)
│   ├── listing/               # 出品ドラフト生成、タイトル/説明文生成、カテゴリ・item specifics 推定
│   ├── pricing/               # 価格戦略・利益計算・価格改定提案
│   ├── orders/                # 受注取り込み、サプライヤー発注の提案(Fulfillment API)
│   ├── supplier/              # サプライヤー在庫・価格の同期、乖離検知(抽象インターフェース。API/CSV両対応)
│   ├── analytics/             # KPI 集計、目標差分、レポート生成
│   ├── approval/              # 承認キュー。提案(Proposal)を人間が承認/却下する仕組み(UI非依存)
│   ├── adapters/ebay/         # eBay Sell API クライアント(認証・レート制限・リトライを内包)
│   ├── prompts/               # 各エージェントのLLMプロンプト(Role/Goal/.../Output JSON)。詳細は AGENT_PROMPTS.md
│   ├── guardrails/            # コンプライアンス・利益・レート制限の検査ロジック(全実行はここを通す)
│   ├── audit/                 # 監査ログ
│   ├── store/                 # DB スキーマ、リポジトリ層
│   ├── api/                   # 承認 UI(Web)用の API(第7フェーズ)
│   └── cli/                   # 承認 UI(CLI)。まずこちらから使えるようにする
└── tests/
```

**設計原則:**
- 外部副作用(eBay への書き込み、サプライヤー発注)は必ず `guardrails/` の検査を通してから実行する
  (「承認済みか」「利益ガードを満たすか」「レート制限内か」「コンプライアンス違反でないか」)。
- `research/` `analytics/` など読み取り系は自動で走ってよい。書き込み系だけがゲート対象。
- eBay 依存は `adapters/ebay/` に閉じ込め、他モジュールは抽象インターフェース越しに使う(将来のマルチPF化のため)。
- **承認 UI は CLI から始めて Web(`api/`)へ拡張する。** そのため `approval/` の承認ロジックは UI 非依存にし、
  `cli/` と `api/` は両方ともこのロジックを呼び出すだけの薄い層にする。
- **サプライヤー連携方式は API/CSV どちらもあり得るため `supplier/` を抽象インターフェースにする。**
  MVP はテスト・検証がしやすい CSV アダプタから実装し、API アダプタは同じインターフェースで後から追加する。

## 5. eBay API 利用方針

**公式ドキュメントを必ず参照して最新の仕様に合わせること**(仕様は変わるため、実装前に developer.ebay.com を確認)。
想定する主な API:

- **認証:** OAuth 2.0(user token / application token)。トークンのリフレッシュを自動化する。
- **リサーチ:** Browse API(競合・相場)、Analytics API(自分の実績・レート上限確認)、Taxonomy API(カテゴリ・aspects)。
- **出品:** Inventory API(inventory item → offer → publish の流れ)を基本にする。
- **受注:** Fulfillment API(注文取得、発送情報の反映)。
- **アカウント/手数料:** Account API(ポリシー、手数料構造の把握)。
- **レート制限:** Developer Analytics の rate limit エンドポイントで残コール数を取得し、コールバジェットに反映する。

**Sandbox 環境で開発・テストし、本番トークンは環境変数(`.env`、コミット禁止)で管理する。**
実際の出品・発注に到達する前に、必ず Sandbox でエンドツーエンドを通すこと。

## 6. 承認ゲート(Human-in-the-loop)の仕様

- 提案は `Proposal` として保存する。フィールド例:
  `id, proposal_type(publish/price_change/withdraw/purchase/hold/none), payload, priority, summary, rationale(根拠), risk_level(low/medium/high), estimated_profit, requires_human_approval, status(pending/approved/rejected/executed/failed), created_at, decided_by, decided_at`。
- **各エージェント(`prompts/` 配下)は、この `Proposal` にそのまま写せる「共通の提案エンベロープ」をJSONで出力する。**
  出力の必須キーは `proposal_type / priority / summary / rationale / risk_level / estimated_profit / requires_human_approval / payload`(`payload` はタイプ別の詳細)。
  各エージェントの完全なプロンプトと入出力例は **`AGENT_PROMPTS.md`** に定義する。`orchestrator` はこのJSONを検証して `proposals` に投入する。
- `proposal_type` の `hold` は「サプライヤー在庫切れ・価格乖離などで一旦保留」、`none` は「アクション不要(据え置き)」を表す。
- 承認 UI は **CLI から始め、Web(`api/`)へ拡張する**。人間が **根拠と影響(価格差・利益・リスク)を見て** 承認/却下する。
- 承認されたものだけを `orchestrator` の Do フェーズが実行する。実行後に結果を `Proposal` に書き戻す。
- **一括承認は可能にするが、リスクレベルが高いもの(大幅値下げ・高額発注)は個別承認を強制する。**
- 却下された提案の理由は学習材料として保存し、同種の提案の閾値調整に使えるようにする。

## 7. データモデル(最低限のテーブル)

- `products` — サプライヤー商品マスタ(原価・在庫・納期・SKU)
- `listings` — eBay 出品(item/offer ID、状態、現在価格、KPI)
- `proposals` — 承認キュー(第6章)
- `orders` — 受注(顧客注文とサプライヤー発注の対応)
- `cycles` — PDCA サイクルの記録(KPI・目標・差分・生成提案)
- `metrics` — 日次/出品別の指標時系列(impression, view, watch, sold, profit)
- `audit_log` — すべての副作用の記録
- `suppliers` — サプライヤー設定(卸直送前提。API/CSV 連携方式を抽象化)

マイグレーション管理を入れること(Alembic)。

## 8. 技術スタック

- 言語: **Python 3.11+**。
- 依存管理: `pyproject.toml`(`pip install -e ".[dev]"` または `uv sync`)。
- Web/API: FastAPI(第7フェーズ)。ジョブ: APScheduler(日次サイクル)。
- DB: 開発は SQLite、本番は PostgreSQL(SQLAlchemy + Alembic)。
- 設定: pydantic-settings + `.env`(秘密情報はコミット禁止)。
- テスト: pytest。外部 API はモック/VCR でテスト。
- LLM 補助(出品文生成・提案生成)を使う場合は、その呼び出しも抽象化し、決定論的にテストできるようにする。

## 9. 開発フェーズ(この順で、各フェーズ完了ごとに動く状態にする)

**第0フェーズ:プロジェクト初期化**(このコミットで完了)
- リポジトリ雛形、依存管理、`.env.example`、`DECISIONS.md`、`README.md` を作る。
- 上記アーキテクチャのディレクトリと空のインターフェースを作る。
- コンプライアンス制約(第1章)を `guardrails/` の TODO とテストのスケルトンに落とす。

**第1フェーズ:eBay アダプタ + 認証(Sandbox)**
- OAuth、トークン管理、レート制限付き API クライアント、リトライ/バックオフ。
- Sandbox で疎通確認(自分のアカウント情報取得など読み取り系から)。

**第2フェーズ:データモデル + 承認基盤**
- DB スキーマ、マイグレーション、`proposals` と承認 CLI/API。
- guardrails の検査ロジック(承認済みか・利益ガード・レート・コンプライアンス)。

**第3フェーズ:Plan(リサーチ + 出品ドラフト生成)**
- Browse/Analytics でリサーチ、利益シミュレーション、出品候補と価格戦略の生成。
- 出品ドラフトを `proposals` に積むところまで(まだ公開しない)。

**第4フェーズ:Do(承認 → 出品/価格改定)**
- 承認済み提案を Inventory API で出品/価格改定。Sandbox でエンドツーエンド。

**第5フェーズ:受注 + サプライヤー同期**
- Fulfillment API で受注取り込み、サプライヤー在庫/価格同期、乖離時の自動保留。
- 発注は提案 → 承認 → 実行。

**第6フェーズ:Check + Act(PDCA を閉じる)**
- KPI 集計、目標差分、改善提案の自動生成、承認キューへの投入。
- orchestrator で全フェーズをスケジュール実行し、日次サイクルで回す。

**第7フェーズ:ダッシュボード + 運用**
- 承認・監視の最小 Web UI、アラート(在庫乖離・レート逼迫・不採算)。

各フェーズの最後に:テストを通す/`README` を更新する/`DECISIONS.md` に設計判断を残す。

## 10. コーディング・品質規約

- 型ヒントを付ける。lint(ruff)+ format(ruff format 相当)を通す。
- 外部副作用のある関数は必ずテストで「guardrails を通っていること」を検証する。
- 秘密情報・トークンをコード/ログに出さない。
- エラーは握りつぶさず、失敗した提案は `failed` として理由を残す。
- コミットは小さく、フェーズ単位で意味のある単位にする。
