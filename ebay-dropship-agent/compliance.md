# eBay 無在庫ドロップシッピング — コンプライアンス参照

> 規約リスクを判断するとき・実装で禁止事項をコード化するときに読む。
> **重要:規約は変わる。実装・運用の判断前に必ず eBay の公式ポリシー(ebay.com のドロップシッピング規約)と
> developer.ebay.com の最新仕様を確認すること。** ここは設計判断のための要点整理であり、最新性を保証しない。

## 1. eBay で許される無在庫 / 禁止される無在庫

- **許される:** 卸売業者・サプライヤーと提携し、注文をそのサプライヤーが顧客へ **直送(drop-ship)** する形態。
  出品者は在庫を持たないが、供給と品質・納期に責任を持つ。
- **禁止(アカウント停止リスク大):** Amazon・Walmart・他のマーケットプレイスや小売店で商品を購入し、
  それを eBay の顧客へ転送する *retail arbitrage(小売アービトラージ)*。
  「他所で買って送るだけ」はこれに該当し、eBay の drop shipping ポリシー違反。

判断の実務:入力・設計に「Amazonから仕入れて」「注文が来たら小売で買って送る」等が出たら、
`proposal_type="hold"` にして `rationale` に「小売アービトラージは規約違反。卸直送のサプライヤーに切り替えが必要」と明記する。

## 2. 出品者責任(無在庫でも免れない)

- **納期:** 出品に記載した handling time / 配送予定を守れること。サプライヤー納期に基づき正直に設定する。
  約束納期を超えそうな受注は発注せず `hold`(顧客連絡が必要)。
- **在庫の正確性:** サプライヤー在庫を同期し、在庫切れの出品は保留・取り下げ提案にする。
- **品質・返品:** 返品・不良対応の責任は出品者にある。返品率を KPI として監視する。
- **真贋・禁止品:** ブランド品の真贋、危険物・禁止カテゴリを事前に除外する。疑わしきは `hold`。

## 3. eBay Sell API(実装で使う正規手段)

- **認証:** OAuth 2.0(user access token / application token)。リフレッシュ自動化。
- **出品:** Inventory API(`inventory_item` 作成 → `offer` 作成 → `publish`)。
- **受注:** Fulfillment API(注文取得 `getOrders`、発送情報反映)。
- **リサーチ:** Browse API(相場・競合)、Taxonomy API(カテゴリ・item aspects)。
- **実績/レート:** Analytics API(トラフィック実績、`getUserRateLimits` で残コール確認)、Account API(ポリシー・手数料)。

## 4. レート制限の考え方

- API ごとに日次コール上限がある(アプリ単位)。`getUserRateLimits` で残数を取得できる。
- 実装では **コールバジェット** を持ち、上限に近づいたら自動で減速・停止する。指数バックオフ + リトライを標準化する。
- 大量出品・頻繁な価格改定はコールを消費する。PDCA サイクル頻度はレート上限と相談して決める。

## 5. 開発時の安全策

- **Sandbox 環境**でエンドツーエンドを通してから本番へ。実出品・実発注の前に必ず検証する。
- 本番トークンは環境変数(`.env`、コミット禁止)で管理する。ログにトークンを出さない。
- すべての副作用(出品・価格変更・発注)は監査ログに残す(誰の承認・いつ・何を・結果)。
